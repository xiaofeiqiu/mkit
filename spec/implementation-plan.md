# mkit 大改版路线图（可执行版）

**目标文档**：给 PM / 同事一眼可读、可落地的路线。版本锚定：`2026-06-07`。

## 0. 先说结论

1. 这次大改版的目的不是“写更多新功能”，而是把系统从“现在能跑”升级为“能持续稳定扩展”。
2. 当前阶段：阶段 0 已完成（100%），阶段 1~4 已有验收产物，阶段 5 收口中。
3. 推荐走法是**保守推进**：先把兼容性和验证链稳定住，再逐步收口兼容层，不做一次性大推倒。
4. 里程碑标准：`make ut`、`make int`、`make docs-check` 贯通且与文档一致。

## 1. 项目背景与意义

### 1.1 你正在做什么

1. 你在做的是一个长期可维护的运行时内核改造，把 `addons/mkit/` 的核心服务、战斗、实体、存档、世界流程重整成清晰边界。
2. 你已在最近两周把大部分基础设施搭好：typed runtime、服务端口迁移、实体访问层、战斗三段模型、save scope、世界恢复链路、文档对齐准备。
3. 但目前集成测试 (`make int`) 仍有残留失败，说明“基础完成”后还有“闭环质量”任务。

### 1.2 为什么要大改版

1. 现状能跑，但边界模糊，重复查找服务和硬编码路径导致改动放大、排障慢。
2. 新内容接入速度受限，游戏端和内核职责容易互相污染。
3. 未来 1~2 个版本会不断叠加补丁，必须在这次改版把入口、边界、事件、持久化收口，否则后续代价更高。

### 1.3 这次改版背后支撑什么

1. 团队交付速度（新玩法接入更快）。
2. 回归风险可控（测试和事件、存档协议可预期）。
3. 运行稳定性（启动/世界/战斗链路异常更少）。
4. 团队协作可见性（文档和阶段验收可直接复用）

## 2. 成功标准与验收定义

### 2.1 业务成功标准

1. 启动可观测、服务可追踪，任意模块故障定位时间下降。
2. 新增或改动内容不改内核层职责，`addons/mkit/` 不直接依赖 `game/`。
3. 战斗、任务、商店、世界、对话链路行为与既定设计一致。
4. `make ut`、`make int`、`make docs-check` 可按周期稳定通过。

### 2.2 技术成功标准

1. 阶段 1~5 的文档和实现无偏差。
2. 兼容层保留在可控范围，逐步可识别可移除。
3. 关键数据边界明确：事件、存档、服务访问、数值模型。
4. 失败可复现可归类，回归链路有负责人。

### 2.3 可测成功率

1. 当前版本基础成功率（阶段1~4）可视作高位启动，按历史可判定为 70%~80%。
2. 在“只修`int`失败并补齐`docs-check`”下，目标成功率提升到 85%。
3. 在“完成收口并回归三门禁”后，目标达到 95%（短期目标），长期向 98% 靠拢。

### 2.4 成功率提升路径

1. 先修关键失败域（场景8、world/quest/dialogue/shop、bootstrap）。
2. 每次只改一个风险域并立即补测试。
3. 按证据闭环推进，`docs` 与 `spec` 与代码保持同步。
4. 阶段5每周做一次门禁复查（ut/int/docs-check）。

## 3. 实施路线（8 个方面）

以下每个方面都含：现实可行路径、理想路径、代价对比。

### 3.1 方面一：阶段5发布收口（现实）

1. 现实路径：先完成 `make int` 全量复核与失败分类，再修复优先域，随后补 `make docs-check`。
2. 理想路径：引入持续集成钩子，三门禁自动失败阻断。
3. 代价对比：现实路径快 30%，理想路径慢但更稳。
4. 行动：把阶段5门禁作为发布前唯一硬门槛，不放行任何未闭环项。

### 3.2 方面二：服务与启动装配收口

1. 现实路径：继续用 `ServiceRegistry.SERVICE_*` 常量并统一高频路径为 `get_port`。
2. 理想路径：完整引入声明化模块生命周期（依赖图 + 自动校验）。
3. 代价对比：现实路径可在现状小改动完成；理想路径涉及更多文件改动，风险高。

### 3.3 方面三：实体契约与组件访问

1. 现实路径：沿用 `EntityContract`，把主要模块节点查找路径移除。
2. 理想路径：把实体访问统一封装为统一 accessor 并覆盖全部路径。
3. 代价对比：现实路径快且稳，理想路径收益高但范围更大。

### 3.4 方面四：战斗与状态域分离

1. 现实路径：以 `DamageIntent -> DamageResolution -> DamageResult` 的链条稳定现状接口。
2. 理想路径：新增 `DamageCalculator` 与完整事件映射，形成可视化命令流。
3. 代价对比：现实路径只补边界，理想路径可观测性更强。

### 3.5 方面五：世界与流程一致性

1. 现实路径：先修复场景8与 world run 的失败，再统一 room/run/reward 事件契约。
2. 理想路径：建立统一 run 生命周期模型并移除重复状态写。
3. 代价对比：现实路径最小化回归风险，理想路径收益高，周期长。

### 3.6 方面六：任务、对话、商店与货币域

1. 现实路径：锁定 `currency_changed`、reward、库存事件的协议，修正状态落点。
2. 理想路径：引入完整 `Wallet` 统一接口，减少裸字典写法。
3. 代价对比：现实路径可快速止血；理想路径可减少长期维护成本。

### 3.7 方面七：文档与引用链完整性

1. 现实路径：`docs/ref`、`spec`、`revamp-tracker` 三者同频更新。
2. 理想路径：文档变更自动校验门禁（文档/规范与代码同步失败阻断）。
3. 代价对比：现实路径低成本，理想路径工程接入成本高。

### 3.8 方面八：组织与协作机制

1. 现实路径：每次提交只改一个失败域，附失败用例和验收结果。
2. 理想路径：建立“阶段负责人 + 风险owner + 审批复核”固定流程。
3. 代价对比：现实路径容易启动；理想路径对组织流程有要求，但长期更稳。

## 4. 三种实施情景（选一个）

1. 情景 A（保守，推荐）：只修故障闭环，保持架构改动不再扩大。风险最小，速度中等。
2. 情景 B（平衡）：在闭环前提下并行补部分理想收口，3~4 周可见显著质量改善。
3. 情景 C（激进）：一次性完成全部声明化模块化目标。收益高，但 `int` 风险大、重构周期不稳定。

优先选择：**情景 B（平衡）**。

## 5. 现有方案 vs 理想方案对比与成本

1. 现有方案优点：改动面小，能把现有失败问题快速修掉。
2. 现有方案缺点：兼容层长期存在，技术债不会降到位。
3. 理想方案优点：边界清晰、长期可扩展、后续版本接入成本低。
4. 理想方案缺点：一次性改动风险高，短期内容易引入新回归。
5. 结论：先现有方案止血，再把理想方案逐块落地，符合现实约束。

## 6. 风险与应对（现实版本）

1. 风险：集成测试持续失败，修复方向发散。
   应对：固定优先级清单，P0修场景8/P1修 world/quest/shop/dialogue/P2再做 docs。
2. 风险：服务与文档边界不同步。
   应对：每次变更前必须标注受影响文档，变更后必补。
3. 风险：兼容层过度保留导致目标飘移。
   应对：阶段收口时对每个兼容点登记“保留原因+移除条件”。
4. 风险：团队沟通不一致。
   应对：周会只看 8 方面清单和三门禁结果。

## 7. 现实时间表（含 2026-06-07）

1. 第 1 周（2026-06-07 起）
   - 锁定 `make int` 失败域，执行 P0A~P1 修复。
2. 第 2 周
   - world / quest / dialogue / shop 连续修复，补充最小回归。
3. 第 3 周
   - `make int` 复绿到可交付目标，补齐 `make docs-check`。
4. 第 4 周
   - 完成阶段5收口门禁，整理发布风险清单。
5. 第 5~6 周
   - 回填理想路径中的低风险收口（日志模板、接口一致性、事件清单）。
6. 第 7~8 周
   - 复盘与稳定化，做一次完整版本发布准备。

现实限制：如果 `make int` 在场景8和 world 仍有长尾问题，计划可顺延 1~2 周。

## 8. 如果不顺利怎么办（应急预案）

1. 先冻结新增改动，只做最小止血。
2. 把失败按域归并：场景、世界、任务、商店、对话。
3. 对每个域出“最小修复包”，优先修可见失败断言。
4. 若出现回归扩散，回退到上一个稳定检查点，重新分批并行修复。
5. 维持 `stage 5` 的门禁：未全部通过的情况下不做发布结论。
