User Manual

Godot Mkit 用户手册

Mkit 是一个 Godot 4.x 2D gameplay kit。它提供可复用的 runtime kernel 和 gameplay modules，用来构建 RPG、roguelike、roguelite、action RPG、dungeon crawler 和 survivor-like 游戏。它不是固定模板，不应该硬编码任何具体游戏内容。

Mkit 提供机制

Command、HFSM、Action、Effect、Stats、Combat、Inventory、Run、Save、UI feedback 等可复用机制属于 kit。

Game 提供内容

具体玩家、敌人、Boss、关卡、技能、物品、剧情、数值、UI 风格、广告经济和平台策略属于你的游戏。

这份手册如何使用

本手册按照目标设计说明 Mkit 的完整使用方式，不以当前实现进度为边界。你可以把它当成接入指南、设计约束和开发 checklist。

Quick Start

这部分不是纯代码教程。Mkit 的接入首先是 Godot 项目配置、文件边界、输入、碰撞层和内容数据库。先把这些基础设好，后面的系统才会稳定。

1. 安装 addon

res://addons/mkit/

推荐项目布局：

res://addons/mkit/     # kit 本体，只放可复用机制
res://game/            # 当前游戏的实体、关卡、内容资源、UI、音频、美术
res://project.godot
边界规则： res://game/ 可以依赖 res://addons/mkit/，但 addon 内不能引用 res://game/ 的具体内容。

2. 启用插件

在 Godot 中打开：

Project > Project Settings > Plugins

启用 Mkit 插件。插件只注册一个真正的全局 autoload：

ServiceRegistry

不要把 EventRouter、CommandRouter、SaveManager、RunDirector 等都做成 Autoload。它们应该由 GameBootstrap 创建，并注册到 ServiceRegistry。

7.1 配置资源池

如果角色有 mana、stamina、energy 或 rage，不要把当前资源值放在 StatsComponent。最大值放在 stats，当前值放在 ResourcePoolComponent。

StatsComponent.base_stats
  max_hp = 100
  max_mana = 50
  max_stamina = 100

ResourcePoolComponent.starting_values
  mana = 50
  stamina = 100

技能定义通过 cost_type 和 cost_amount 消耗资源：

AbilityDefinition
  ability_id = "ability.fireball_basic"
  cost_type = "mana"
  cost_amount = 15

AbilityDefinition
  ability_id = "ability.dash"
  cost_type = "stamina"
  cost_amount = 25
关键规则：最大资源随装备、升级、buff 变化时由 StatsComponent 计算；当前资源由 ResourcePoolComponent clamp 到新的最大值。这样 UI、AbilityController、SaveManager 都有稳定数据来源。

核心概念

这些概念是 Mkit 的共同语言。团队中所有 gameplay、UI、数据和工具代码都应该遵守同一套边界。

Definition Resource

是什么：静态内容数据，通常是 Godot Resource。

为什么需要：设计师可以在 Inspector 配置；同一份定义可生成多个实例；存档可以保存 stable ID。

什么时候需要：物品、技能、状态、房间、敌人、升级、掉落表、奖励选项。

用例：item.sword_iron 定义攻击 +5，掉落三把时生成三个不同 ItemInstance。

Runtime Instance

是什么：definition 在运行时产生的可变实例。

为什么需要：技能冷却、物品数量、状态层数、房间清理状态、run 进度都不能写回静态定义。

什么时候需要：只要数据会变化，就创建 instance。

用例：ability.fireball_basic 是定义；玩家身上的火球剩余冷却 3 秒是 AbilityInstance。

Component

是什么：挂在实体上的局部能力和状态。

为什么需要：用组合替代继承，让 Health、Stats、Hitbox、Hurtbox 可以复用。

什么时候需要：某项能力属于一个实体，并随实体生命周期存在。

用例：HealthComponent 同时可用于玩家、敌人、箱子和召唤物。

Controller

是什么：挂在实体或系统节点上的流程协调器。

为什么需要：能力、背包、装备、状态要管理多个 runtime instance。

什么时候需要：一个实体拥有多项可管理能力时。

用例：AbilityController 检查冷却、消耗、条件，然后启动 CastAction。

System / Resolver

是什么：跨实体规则和全局流程。

为什么需要：伤害、掉落、奖励、存档、房间推进不能散落在实体内部。

什么时候需要：逻辑涉及多个实体、全局配置、随机种子或跨模块协调。

用例：CombatResolver 根据 attacker stats 和 target stats 产出 DamageResult。

Command

是什么：意图，不是结果。

为什么需要：统一玩家输入、AI、脚本、自动化测试和回放。

什么时候需要：移动、攻击、施法、交互、选择奖励、打开背包、暂停。

用例：玩家按 Space 发 attack，Dead 状态拒绝，Idle 状态进入 BasicAttack。

HFSM

是什么：层级有限状态机，管理行为模式。

为什么需要：复杂角色会有 Alive、Dead、Locomotion、Combat、Casting、Stunned 等层级关系。

什么时候需要：实体行为、房间生命周期、run 生命周期。

用例：Player/Alive/Combat/BasicAttack 可以被 death 事件全局打断到 Player/Dead。

Action

是什么：随时间执行、可取消、可完成的过程。

为什么需要：攻击前摇/生效/后摇、冲刺、施法读条、等待动画、持续引导都不是瞬时结果。

什么时候需要：任何需要 update、cancel、complete 的 gameplay 过程。

用例：TimedAttackAction 在 active frame 打开 hitbox，结束后通知状态返回 Idle。

Condition

是什么：可复用规则检查。

为什么需要：技能、装备、奖励、AI、状态转换都会重复检查条件。

什么时候需要：目标范围、冷却、魔法、标签、生命比例、房间清理、随机概率。

用例：Fireball 同时要求 cooldown ready、mana enough、target in range。

Effect

是什么：声明式 gameplay 结果。

为什么需要：技能、物品、奖励、状态 tick 都会产生类似结果，应该复用。

什么时候需要：伤害、治疗、应用状态、生成场景、发物品、修改属性、播放 VFX。

用例：Poison 每秒执行 DealDamageEffect，药水执行 HealEffect。

Event

是什么：已经发生的事实。

为什么需要：UI、音频、VFX、分析、成就和任务系统都需要解耦监听。

什么时候需要：damage_applied、entity_died、room_cleared、reward_selected。

用例：Health 到 0 发 entity_died，RoomController 和 FeedbackSystem 同时监听。

GameplayContext

是什么：一次行为执行时的上下文对象。

为什么需要：比散乱 Dictionary 更清晰，减少 key 拼写错误。

什么时候需要：Action、Effect、Condition、Ability、Reward。

用例：source=player、target=goblin、ability_id=fireball、position=mouse_pos。

Stable ID、Runtime ID、Tag、Faction

概念 用途 示例 规则
Stable ID 长期内容标识，可存档、查表、分析 item.sword_iron 进入存档或发布后不要随意改名
Runtime ID 某个运行时实例的唯一标识 item_instance_000123 用于区分同一 definition 的多个实例
Tag 横向分类、条件判断、抗性、AI 策略 fire、boss、projectile 适合组合，不适合表达唯一身份
Faction 阵营和敌我判断 player、enemy、neutral Hitbox target filtering 优先使用 faction

Runtime Kernel Components

Runtime Kernel 是所有 gameplay modules 依赖的底层机制。它应该保持通用，不引用具体游戏内容。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
GameBootstrap游戏启动协调节点，创建服务、加载内容、进入初始场景。启动顺序明确，避免多个 Autoload 互相依赖。每个项目主场景都需要。启动后注册 EventRouter、ContentRegistry、CommandRouter、RunDirector。写入 ServiceRegistry，读取 ResourceDatabase，调用 SceneRouter。
ServiceRegistry单一全局服务定位器。允许系统按 ID 获取服务，方便 mock 和平台替换。获取 random、time、events、content、save、analytics 等服务时。ServiceRegistry.get_service("events")。被所有模块读取，但不应存放普通 gameplay 对象。
ContentRegistrystable ID 到 Resource 的索引。大量 RPG 内容需要统一查找和校验。技能、物品、房间、敌人、奖励、升级都用 ID 引用时。存档保存 item.sword_iron，加载时查 Resource。由 GameBootstrap 加载 ResourceDatabase，被各系统查询。
ResourceDatabase一组 Resource 的数据库资源。让设计师分批组织内容。每类内容可有一个或多个数据库。db_abilities.tres 收集所有 AbilityDefinition。被 ContentRegistry 加载。
ContentValidationResult内容校验结果。发现重复 ID、空 ID、缺失引用。编辑器校验、启动校验、CI 测试。启动时输出 duplicate content id。由 ContentRegistry 产生。
EventRouter领域事件路由器。UI、音频、VFX、分析可以解耦监听 gameplay。当某件事已经发生，需要通知旁观系统。damage_applied 后 DamageNumberSystem 显示数字。Domain system 发事件，Feedback/UI/Analytics 监听。
DomainEvent通用事件数据结构。便于日志、调试、回放、遥测。需要统一事件流时。DebugOverlay 显示最近 5 个 event type。由 EventRouter 保存 recent events。
GameCommand意图数据对象。统一输入、AI、脚本、测试来源。任何 gameplay 请求入口。cast_ability 携带 ability_id 和 target_id。由 InputReader/AI 创建，交给 CommandRouter。
CommandRoutercommand 分发器。按 target_id 找到对应 CommandReceiver。多个实体都能接收 command 时。AI 对 goblin_01 发 attack command。维护 receiver map，发出 command_failed。
CommandReceiver实体上的 command 接收节点。把外部意图交给实体 HFSM。每个可被控制或被 AI 驱动的实体。玩家、敌人、RunDirector、UI 都可以有 receiver。调用 StateMachine.handle_command。
StateMachineHFSM 运行器。管理当前状态、层级转换、update、transition guard。实体、房间、run 的行为模式复杂时。Player 从 Move 切到 BasicAttack。持有 Blackboard，调用 State。
State行为模式节点。封装 enter、exit、update、command 处理。Idle、Move、Attack、Dead、RoomCombat 等模式。AttackState 启动 TimedAttackAction。可请求 StateMachine transition。
Blackboard状态机共享临时数据。sibling state 之间需要共享方向、目标、临时参数。facing、move_direction、current_target。MoveState 写入 facing，AttackState 使用 facing 摆放 hitbox。属于 StateMachine，被 State 读写。
GameAction可更新、可取消、可完成的过程。攻击、冲刺、施法、等待动画都需要时间。任何不是瞬时的行为。DashAction 持续 0.2 秒。由 State 或 Controller 创建，交给 ActionRunner。
ActionRunner更新所有 active action。将 timed process 从 State 中抽离。需要统一暂停、time scale、cancel 时。暂停游戏后 action delta 变 0。读取 TimeService，发 action_completed。
ActionContextaction 执行上下文。Action 需要 source、target、direction、duration。启动任意 action。CastAction 读取 ability_id 和 source。继承 GameplayContext。
Condition可配置条件 Resource。减少重复规则判断。技能、装备、奖励、AI、transition guard。TargetInRangeCondition。被 ConditionEvaluator 调用。
ConditionEvaluator条件组评估器。统一 all/any/failure reason 规则。检查多个条件时。AbilityController 检查 cooldown、mana、range。被 GameEffect、AbilityController、RewardSystem 使用。
GameEffect声明式 gameplay 结果。可复用、可配置、可调试。技能、物品、奖励、状态 tick。DealDamageEffect、HealEffect、GrantItemEffect。被 EffectExecutor 执行。
EffectExecutoreffect 执行器和 trace 记录。集中记录成功、失败、child results。一次执行一个或多个 effects 时。RewardSystem apply selected option。调用 ConditionEvaluator，返回 EffectResult。
EffectResulteffect 执行结果。调试失败原因和下游逻辑。effect 可能失败或需要返回数据时。GrantItemEffect 返回 instance_id。被 EffectExecutor 和 DebugOverlay 使用。
GameplayContext行为上下文。避免散乱 Dictionary 和 key 拼写错误。effect、condition、ability、reward 都需要上下文。source=player,target=goblin,ability_id=fireball。贯穿 Action、Condition、Effect、Domain System。
RandomService可种子的随机服务。roguelike 需要可复现随机。掉落、房间生成、暴击、奖励权重。同 seed 生成同一条地牢路线。被 LootSystem、DungeonGenerator、CombatResolver 使用。
TimeServicegameplay 时间服务。支持暂停、慢动作、time scale。action、status tick、cooldown 都要受暂停影响。打开奖励选择时暂停 gameplay timer。被 ActionRunner、StatusEffectController、RunDirector 使用。
SceneRouter场景切换服务。控制转场、避免重复切换。从菜单进 run、重开、回主菜单。Run failed 后切到 GameOverScene。被 GameBootstrap、RunDirector、UIManager 使用。
ObjectPool对象池。投射物、伤害数字、VFX 频繁创建销毁。高频 spawn/despawn 对象。火球 projectile 从 pool 获取。被 SpawnSceneEffect、VFXSpawner、ProjectileSystem 使用。
DebugOverlay调试显示层。可复用框架必须可观察。开发和 QA 验证 vertical slice。显示 state path、last command、HP、recent events。读取 StateMachine、CommandReceiver、EventRouter。

Entity / Stats / Health / Combat

这些模块构成动作 RPG 的基础战斗闭环。HFSM 负责行为模式，Action 负责时序，CombatResolver 负责公式，HealthComponent 负责 HP 状态，EventRouter 负责通知。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
EntityIdentity实体身份、definition、faction、tags。让系统稳定识别实体。所有可参与 gameplay 的实体。goblin_01，faction enemy，tag melee。被 CommandReceiver、Hitbox、EventRouter、Save 使用。
EntityRoot实体根节点和组件访问入口。统一查找 Components、Controllers、Identity。玩家、敌人、召唤物、陷阱、NPC。get_component("HealthComponent")。持有子组件，不承担具体规则。
EntityDefinition实体静态定义。数据驱动生成敌人、NPC、掉落物。需要从 ID 生成实体时。enemy.goblin_basic 指向 goblin scene。被 EntitySpawner 和 ContentRegistry 使用。
EntitySpawner实体生成器。统一 spawn、初始化 identity、挂接父节点。房间刷怪、召唤物、投射物、掉落物。RoomController 根据 spawn rules 生成 enemy。读取 EntityDefinition，可能使用 ObjectPool。
StatsComponent基础属性和 modifier 计算。RPG 数值都需要统一计算。HP、攻击、防御、移速、暴击、冷却、幸运。装备剑后 attack_power 增加。被 CombatResolver、HealthComponent、AbilityController 使用。
StatDefinition属性定义。让属性有显示名、默认值、上下限、是否百分比。设计属性系统、UI 显示和校验。crit_chance 是百分比。被 ContentRegistry 和 Stats UI 使用。
StatModifierDefinition静态 modifier 配置。装备、buff、升级都能复用。需要定义一个固定属性加成。upgrade.attack_plus_20 给 attack_power +20%。生成 StatModifier。
StatModifier运行时 modifier。有 source、duration、stacking rule。临时 buff、装备加成、状态 debuff。burn 降低 defense 5 秒。被 StatsComponent 管理。
HealthComponentHP 状态和死亡入口。HP 是独立于伤害公式的实体状态。玩家、敌人、可破坏物。apply DamageResult 后 HP 到 0，emit died。读取 StatsComponent max_hp，发 EventRouter event。
ResourcePoolComponent实体的可消耗资源池，例如 mana、stamina、energy、rage。AbilityController 有 cost_type/cost_amount；没有统一资源池时，技能消耗会被写死在玩家脚本里。任何有技能消耗、冲刺体力、怒气、能量、读档恢复资源的实体。火球 cost_type=mana、cost_amount=15，释放前检查 mana，成功后扣除。当前值存在 ResourcePoolComponent；最大值从 StatsComponent 读取 max_mana、max_stamina；AbilityController 调用 has_resource/spend；HUD 监听 resource_changed。
DamageRequest伤害请求。把攻击来源、目标、基础伤害、类型、tag 放在一起。hitbox、projectile、damage effect 都可创建。火球命中敌人创建 fire damage request。输入给 CombatResolver。
DamageResult伤害计算结果。记录 final damage、crit、block、evade、trace。需要应用伤害和显示反馈时。UI 显示暴击 48，Debug 显示公式 trace。输入给 HealthComponent 和 EventRouter。
CombatResolver战斗公式解析器。集中处理攻击、防御、暴击、抗性、格挡、闪避。任意伤害发生前。读取 source attack_power 和 target defense。输出 DamageResult，不播放 VFX，不发 loot。
HitboxComponent攻击判定区域。动作帧和碰撞检测需要解耦。近战攻击、陷阱、范围技能。active frame 打开 hitbox。创建 DamageRequest，调用 CombatResolver。
HurtboxComponent受击判定区域。目标受击区域可能和身体不同。玩家、敌人、弱点、盾牌。Boss 头部 hurtbox 有 damage_multiplier 1.5。被 HitboxComponent 检测。

Ability / Status Effect

Ability 负责主动或被动技能，Status Effect 负责 buff、debuff、dot、hot 和临时机制。两者都依赖 Condition、Action、Effect 和 GameplayContext。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
AbilityDefinition技能静态数据。设计师可配置 cooldown、cost、range、effects。主动技能、被动技能、怪物技能。ability.fireball_basic。被 ContentRegistry 查找，生成 AbilityInstance。
AbilityInstance技能运行时状态。冷却、充能、等级、启用状态会变化。玩家或敌人拥有技能后。火球剩余冷却 2.4 秒。被 AbilityController 管理。
AbilityController实体技能控制器。集中检查条件、资源消耗、冷却、施法和效果执行。玩家、敌人、Boss、召唤物可释放技能。收到 cast_ability command 后检查 mana/stamina，启动 CastAction，完成后执行 effects。调用 ResourcePoolComponent 检查并扣除 cost，调用 ConditionEvaluator、ActionRunner、EffectExecutor。
CastAction施法过程。读条、动画、打断、施法完成时机。有 cast_time 或 channel 的技能。火球读条 0.4 秒，沉默可打断。由 AbilityController 或 State 启动。
Projectile投射物实体或场景。许多技能需要空间移动和碰撞。火球、箭、飞刀、弹幕。SpawnSceneEffect 生成 projectile。命中后创建 DamageRequest 或执行 effects。
StatusEffectDefinition状态静态配置。duration、tick、stack、modifier、effects 可配置。burn、poison、slow、stun、shield、rage。status.burn 每秒伤害。被 ContentRegistry 查找。
StatusEffectInstance状态运行时实例。剩余时间、层数、tick timer 会变化。状态应用到实体后。毒有 3 层，剩余 4.5 秒。被 StatusEffectController 管理。
StatusEffectController实体状态控制器。处理 apply、remove、stack、tick、modifier。任何可被 buff/debuff 的实体。敌人被 burn，tick 执行 DealDamageEffect。调用 StatsComponent 和 EffectExecutor。
CooldownReadyCondition冷却条件。技能和物品使用需要冷却限制。能力或道具有 cooldown。火球 cooldown 未完成则不能施放。被 AbilityController 检查。
TargetInRangeCondition距离条件。技能、AI、交互都需要范围判断。近战攻击、法术、NPC 对话。敌人在 64 px 内才可攻击。被 ConditionEvaluator 使用。

Ability cast flow

  1. InputReader 或 AI 创建 CastAbilityCommand。
  2. HFSM 检查当前状态是否允许施法，例如 Dead、Stunned、Silenced 状态拒绝。
  3. AbilityController 读取 AbilityDefinition，检查 cooldown、charges、conditions、range 和 cost_type/cost_amount。
  4. 如果技能需要资源，AbilityController 通过 ResourcePoolComponent.has_resource() 检查 mana、stamina、energy 或 rage；确认释放后调用 spend() 扣除。
  5. CastAction 播放动画、进入读条，并允许被 stun、death、silence 等 cancel tag 打断。
  6. 到达配置的 effect timing 后，EffectExecutor 执行 effects。
  7. 技能启动 cooldown，EventRouter 发 ability_cast / cooldown_started，HUD 更新资源条和技能冷却。

Ability resource interaction

资源消耗分为最大值和当前值两个来源：最大值是 stat，例如 max_mana、max_stamina；当前值是 resource pool，例如当前 mana=35、当前 stamina=80。这样装备、buff、升级可以通过 StatsComponent 改最大资源，而技能释放、药水、读档只修改当前资源。

AbilityDefinition
  cost_type = "mana"
  cost_amount = 15
  cooldown = 3.0
  effects = [DealDamageEffect, ApplyStatusEffect]

AbilityController.cast()
  -> get AbilityInstance
  -> check cooldown / charges
  -> ConditionEvaluator.evaluate_all()
  -> ResourcePoolComponent.has_resource("mana", 15)
  -> ResourcePoolComponent.spend("mana", 15)
  -> CastAction or immediate effects
  -> AbilityInstance.start_cooldown()
  1. 资源不足时，cast() 应该失败并发出明确 reason，例如 Not enough resource: mana。
  2. 资源不足时不应该启动 cast action，不应该执行 effects，也不应该进入 cooldown。
  3. HUD 应该同时监听 resource_changed 和 cooldown_started，资源条和技能图标分别刷新。
  4. SaveManager 保存当前资源值；StatsComponent 或 ProgressionSystem 恢复最大资源来源。

Status tick flow

  1. ApplyStatusEffect 或 DamageRequest.on_hit_statuses 请求应用状态。
  2. StatusEffectController 根据 stack rule 刷新、叠层、替换、忽略或独立存在。
  3. 执行 effects_on_apply，并把 stat_modifiers 添加到 StatsComponent。
  4. 每到 tick_interval 执行 effects_on_tick。
  5. duration 结束时执行 effects_on_remove，并移除 stat_modifiers。

Inventory / Equipment / Loot / Reward

Inventory 和 Equipment 处理玩家拥有的物品，Loot 负责生成结果，Reward 负责玩家面前的选择。UI 只展示和提交意图，不直接修改属性或背包。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
ItemDefinition物品静态定义。名称、图标、稀有度、效果、装备加成都应数据化。装备、消耗品、材料、货币、钥匙。item.potion_small 有 HealEffect。被 ContentRegistry、LootSystem、Inventory 使用。
ItemInstance物品运行时实例。数量、耐久、词缀、升级等级会变化。背包中实际拥有的物品。一把 +12% crit 的铁剑。保存 definition_id 和 runtime metadata。
InventorySlot背包格子。slot-based inventory 需要位置和堆叠。格子背包、快捷栏、仓库。slot 3 有 5 个 potion。属于 InventoryModel。
InventoryModel背包数据模型。UI 和 Controller 都需要纯数据结构。需要序列化或预览背包。保存 slots 数组。被 InventoryController 修改。
InventoryController背包操作控制器。添加、移除、堆叠、移动、保存、发事件。玩家、宝箱、商店库存。拾取药水后 add_item。发 inventory_changed，供 UI 刷新。

LootRollResult掉落结果。掉落生成不应立刻修改背包。需要先生成再决定落地或直接发放。宝箱打开生成 3 个选项。传给 PickupSpawner 或 RewardSystem。

RewardOption玩家可选奖励。UI 需要显示和执行一组选项。选择升级、选择物品、选择技能。+20% attack 作为一张卡。包含 display data、conditions、effects、weight。
RewardSystem奖励生成和应用系统。选择逻辑不能写在 UI 里。房间清理后、升级时、商店购买时。生成三选一并 apply selected option。调用 EffectExecutor，发 reward_selected。

Reward interaction

Enemy died
  -> RoomController remaining enemies = 0
  -> EventRouter.room_cleared
  -> RunDirector enters ChoosingReward
  -> RewardSystem.generate_options()
  -> UIManager opens RewardSelectionUI
  -> Player selects RewardOption
  -> RewardSystem.apply_selected()
  -> EffectExecutor executes effects
  -> RunDirector advances to next room

Run / Room / Procedural Generation / Progression

这些模块构成 roguelike 局内循环。Room 处理当前房间，Run 处理整局游戏，DungeonGenerator 根据 seed 生成路径，Progression 处理局内和局外成长。

RoomRuntime房间运行时状态。当前是否清理、敌人实例、奖励状态会变化。进入房间后。active enemy count = 3。被 RoomController 持有。

Room HFSM房间状态机。房间从加载到完成有明确生命周期。复杂房间、Boss 房、事件房。Unloaded -> Loading -> Active -> Cleared。被 RoomController 驱动。

AI / Interaction / UI / Feedback

这些模块把 gameplay 和玩家体验连接起来，但不应该破坏核心边界。AI 产生 command；UI 表达用户意图并响应事件；Feedback 监听事件并播放表现。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
EnemyBrainAI 决策入口。敌人需要根据环境产生意图。敌人、Boss、召唤物、NPC。看到玩家后发 chase command。创建 GameCommand，不直接改状态。
SimpleAI简单规则 AI。快速验证战斗循环。追玩家、近身攻击、低血逃跑。goblin if in range attack else chase。使用 Condition 和 CommandRouter。
BehaviorTreeAI行为树 AI。Boss 和复杂敌人需要结构化决策。多阶段、巡逻、技能组合。Selector: attack if in range else chase。叶子节点发 command。
UtilityAI效用 AI。高级动态选择行为。后期复杂 Boss 或策略敌人。在逃跑、攻击、召唤中选最高效用。不应早于核心循环实现。
InteractionComponent交互能力组件。玩家和世界对象需要统一交互入口。NPC、门、宝箱、祭坛、拾取物。玩家按 E 发 interact command。调用 Interactable 或发 domain request。
Interactable可交互对象接口。世界对象需要暴露交互条件和结果。门、宝箱、商店、NPC。宝箱打开后请求 LootSystem。使用 Condition 和 Effect。
UIManagerUI 流程管理。弹窗、暂停、输入阻挡、screen stack 需要集中处理。inventory、reward、pause、shop。打开奖励界面并阻止 gameplay input。监听 events，发送 commands 或调用 domain API。
RewardSelectionUI奖励选择界面。三选一奖励是 roguelike 核心体验。房间清理、升级、Boss 奖励。显示 3 张 RewardOption 卡。用户点击后通知 RewardSystem。
HUD局内状态展示。玩家需要 HP、技能冷却、资源、run 进度。所有 gameplay 场景。显示 HP bar 和 cooldown icons。监听 Health、Ability、Run events。
FeedbackSystem反馈协调器。gameplay 不应直接播放所有 VFX/audio。命中、暴击、死亡、拾取、奖励。damage_applied 后播放 hit feedback。监听 EventRouter，调用 Audio/VFX/DamageNumber。
AudioManager音频服务。音量、bus、随机音效、优先级需要集中。hit、death、ui click、reward。播放 sword_hit_01。由 FeedbackSystem 或 UIManager 调用。
VFXSpawnerVFX 生成器。VFX 需要 pooling、anchor、layer 管理。命中、爆炸、治疗、拾取。在 hurtbox position 生成 hit spark。使用 ObjectPool。
DamageNumberSystem伤害数字系统。战斗反馈需要统一格式和 pooling。damage_applied、heal、crit。暴击数字更大更亮。监听 EventRouter，读取 DamageResult。

UI flow

玩家点击装备按钮
  -> InventoryUI 发送 EquipItemCommand 或调用 EquipmentController API
  -> EquipmentController 校验槽位并装备
  -> StatsComponent 重新计算属性
  -> EventRouter 发 inventory_changed / equipment_changed / stat_changed
  -> UI 从 view model 刷新

Feedback flow

Combat event emitted
  -> FeedbackSystem receives event
  -> VFXSpawner spawns hit effect
  -> AudioManager plays hit sound
  -> DamageNumberSystem displays number

Save / Progression / Platform Services

这些模块让游戏从 demo 变成可发布产品。先接 mock 服务，再接真实平台 SDK。

Component 概念解释 为什么需要 什么时候需要 场景用例 交互关系
Saveable可保存对象契约。SaveManager 不应了解每个系统内部结构。需要持久化的系统。InventoryController 实现 to_save_data。被 SaveManager 扫描或注册。
SaveManager存档协调器。统一写文件、读文件、版本、profile。任何需要持久化的游戏。保存 player、inventory、progression、settings。调用 Saveable，使用 File System 和 SaveMigration。
SaveMigration存档迁移。游戏更新后旧存档结构可能变化。版本升级。save_version 1 升到 2。被 SaveManager 在 load 时调用。
AnalyticsService分析接口。记录 run、死亡、奖励选择、留存事件。需要产品数据时。track run_finished。监听 EventRouter 或由 systems 调用。
AnalyticsServiceMock分析 mock。本地开发不能依赖外部 SDK。开发、测试、CI。print analytics payload。注册到 ServiceRegistry。
AdService广告接口。移动端 rewarded ad、interstitial。需要广告变现。看广告复活或双倍奖励。UI 调用服务，RewardSystem 发放结果。
AdServiceMock广告 mock。本地验证广告流程。Editor 和测试。立即返回 rewarded success。替换真实 AdService。
IAPService内购接口。商品、购买、恢复购买。有付费商品时。购买 starter pack。调用平台 SDK，发 purchase event。
IAPServiceMock内购 mock。不接 SDK 也能开发商城。Editor 和测试。假购买成功。替换真实 IAPService。
CloudSaveService云存档接口。跨设备保存和冲突解决。移动端或平台账户。上传 profile save。被 SaveManager 可选调用。

Save rules

  • 存 stable ID，不存脆弱节点路径。
  • 存长期状态，不存短暂动画帧。
  • ResourcePoolComponent 保存当前 mana/stamina/energy/rage；StatsComponent 或 ProgressionSystem 保存最大资源的来源。
  • mid-run save 只存能安全恢复的 run state。
  • 读取后把实体行为恢复到安全状态，例如 Idle。

  -> HealthComponent HP 到 0
  -> HealthComponent 发 died
  -> EntityDeathSystem 或对应 Controller 处理死亡流程
  -> Enemy HFSM 进入 Dead
  -> LootSystem 生成掉落
  -> RoomController 更新清场条件
  -> FeedbackSystem 播放死亡反馈

  • Runtime instance 另有 instance_id。

创建一个新技能

  1. 创建 AbilityDefinition。
  2. 设置 ability_id、display name、cooldown、cost、cast time、range。
  3. 如果技能消耗资源，设置 cost_type 为 mana、stamina、energy 或 rage，并确保实体有 ResourcePoolComponent。
  4. 添加 conditions，例如 cooldown ready、target in range、has tag；资源检查由 AbilityController 通过 ResourcePoolComponent 处理。
  5. 添加 effects，例如 SpawnSceneEffect、DealDamageEffect、ApplyStatusEffect。
  6. 把 AbilityDefinition 加入 ResourceDatabase。
  7. 在玩家或敌人的 AbilityController 中注册该 ability。
  8. 在 InputReader 或 AI 中发 cast_ability command。
  9. 在 HUD 中监听 cooldown、ability events 和 ResourcePoolComponent.resource_changed。

创建一个新状态效果

  1. 创建 StatusEffectDefinition。
  2. 设置 status_id、duration、tick_interval、max_stacks、stack_rule。
  3. 配置 stat_modifiers，例如 slow 降低 move_speed。
  4. 配置 effects_on_apply、effects_on_tick、effects_on_remove。
  5. 把 StatusEffectDefinition 加入 ResourceDatabase。
  6. 用 ApplyStatusEffect 或 DamageRequest.on_hit_statuses 应用状态。
  7. 在 UI 中监听 status events 显示图标和层数。

创建一个新物品

  1. 创建 ItemDefinition。
  2. 设置 item_id、type、rarity、icon、stackable、max_stack。
  3. 消耗品配置 use_conditions 和 use_effects。
  4. 装备配置 equipment slot 和 stat_modifiers。
  5. 把 ItemDefinition 加入 ResourceDatabase。
  6. 把 item_id 加入 LootTableDefinition 或 RewardDefinition。
  7. 实现 UI 显示和使用入口。

如果物品恢复资源，例如 mana potion，不要直接改 StatsComponent.max_mana。应通过 effect 或 inventory use flow 调用 ResourcePoolComponent.restore("mana", amount)。

创建一个新敌人

  1. 创建敌人 scene。
  2. 配置 EntityIdentity，faction = enemy。
  3. 添加 StatsComponent、HealthComponent、HurtboxComponent、HitboxComponent。
  4. 添加 CommandReceiver、EnemyBrain、StateMachine。
  5. 实现 Idle、Chase、Attack、Dead 状态。
  6. 创建 EntityDefinition，指向该 scene。
  7. 配置 loot table 和 spawn weight。
  8. 把 EntityDefinition 加入 ResourceDatabase。
  9. 在 RoomDefinition.spawn_rules 中引用敌人 ID。

创建一个新房间

  1. 创建 room scene。
  2. 添加 RoomController、spawn points、doors、reward anchor。
  3. 创建 RoomDefinition，设置 room_id、scene_path、room_type、difficulty、size、tags。
  4. 配置 spawn_rules 和 reward_rules。
  5. 把 RoomDefinition 加入 ResourceDatabase。
  6. 在 DungeonGenerator 的 generation rules 中允许该 room type。

创建一个奖励池

  1. 创建 RewardDefinition。
  2. 配置候选 RewardOption 或引用 upgrade/item/ability pools。
  3. 给每个 option 设置 weight、rarity、conditions、effects。
  4. 把 RewardDefinition 加入 ResourceDatabase。
  5. RoomController 或 RunDirector 在 room clear 后请求 RewardSystem 生成 choices。
  6. RewardSelectionUI 展示 choices。
  7. 玩家选择后 RewardSystem 应用 effects。

调试和排错

Mkit 的调试能力不是可选项。可复用 framework 如果不可观察，就很难用于真实项目。

DebugOverlay 至少显示

  • 当前 HFSM state path。
  • 上一个 state path。
  • 最后收到的 command。
  • 最后 transition reason。
  • 失败 transition reason。
  • active actions。
  • 当前 resource pools，例如 mana 35 / 50、stamina 80 / 100。
  • active status effects。
  • 当前 stat values。
  • active stat modifiers。
  • 最近 damage calculation trace。
  • 当前 room state。
  • 当前 run state。
  • random seed 和 stream state。
  • 最近 domain events。

常见问题

现象 优先检查
command 没反应target_id 是否匹配 CommandReceiver receiver_id。
状态没有切换State path 是否正确，can_enter/can_exit 是否返回 false。
攻击打不到collision layer/mask、hitbox active frame、hurtbox owner_path。
伤害为 0DamageRequest source/target、StatsComponent、defense、damage tags。
UI 不刷新是否监听 EventRouter 或对应 component signal。
技能一直提示资源不足实体是否有 ResourcePoolComponent；cost_type 是否和 resource_id 一致；StatsComponent 是否提供 max_mana、max_stamina 等最大值。
存档读不回内容stable ID 是否还存在于 ContentRegistry。
随机结果不可复现是否所有随机都走 RandomService。
暂停后 action 还在跑action 是否通过 TimeService scaled delta 更新。

设计边界和反模式

必须保持的边界： Mkit 提供可复用机制，game/ 提供具体内容和规则。

Mkit 应该知道

AbilityDefinition、ItemDefinition、DamageRequest、RewardOption、RunState、RoomDefinition、Condition、Effect、Command、State。

Mkit 不应该知道

Red Mage 的 Fireball 剧情特效、Goblin King 的具体掉落、第二章 Iron Sword 文案、某个广告复活经济规则、某个商店具体定价策略、某条故事线进度。

反模式和替代方案

反模式 问题 替代方案
InputReader 直接改 HP绕过状态和战斗系统。发 command，由 HFSM 和 Combat 处理。
CombatResolver 播放音效战斗和表现耦合。发 event，FeedbackSystem 播放。
Reward UI 直接改 StatsUI 和规则耦合。RewardSystem apply effects。
SaveManager 硬编码 Player scene无法复用和迁移。Saveable contract。
所有系统都 Autoload启动顺序混乱，难测试。只 Autoload ServiceRegistry。
Definition 存运行时状态多实例互相污染。Definition + Runtime Instance 分离。
AI 直接调用状态函数绕过 command pipeline。AI 只产生 GameCommand。

推荐开发顺序

按 vertical slice 开发，不要按系统孤岛开发。第一阶段不要追求所有系统完整，先证明核心管线。

Command -> HFSM -> Action -> Effect -> Combat -> Event -> UI/VFX
Phase 目标 验收
0Kernel prototypecommand 进入 HFSM，action 执行，effect 记录，debug 可见。
1Combat vertical slice玩家移动攻击，敌人受伤死亡，事件发出。
2Ability and status火球、冷却、投射物、burn/poison tick。
3Inventory and equipment掉落、拾取、背包、装备、属性变化。
4Room and run进入房间、清场、奖励、下一房间、失败或通关。
5Save and progression通关获得货币，购买永久升级，重启后保留。
6Platform servicesanalytics、ads、iap、cloud save 先接 mock，再接 SDK。
